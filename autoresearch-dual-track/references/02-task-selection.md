# 选题与正式消费预检

## 进入长轨迹前必须回答

1. 优化面是否允许方法级变化，而非固定数字或有限集合的昂贵枚举？
2. 指标、方向、Baseline、上界/下界、有效改善阈值和质量门是否在题面冻结？
3. 当前协议需要不同 training seed、同 seed replicate，还是确定性评估？按来源执行，不自行加门槛。
4. 便宜 pilot 的 Baseline 波动和候选效应量是多少？候选能否在预算内越过统计与归一化门？
5. 一个正式结果能否一对一回指 run/trial ID、代码、配置、seed、日志、checkpoint、receipt 和 artifact？
6. 目标 Harness backend、模型/数据来源、受信输入、权限和 reward 路径是否明确？
7. 一次迭代多久、两条轨迹分别需要多久、正式补测需要保留多少窗口？

缺少 2、3、5 或 6 时先补合同；pilot 显示信号弱于门槛时优先换优化面。长时间 Agent 运行不能补救不可判定的题目。

## seed 与 replicate

`training_seed`、`replicate_id`、`run_id` 分开。多个同 seed 独立训练可以估计该 seed 下的重复性，但只有当平台协议允许时才足以支持正式结论；不能改标签冒充不同 seed。反过来，若平台只要求同 seed 重复，也不能事后发明跨 seed 门槛推翻原协议。补充 seed 作为敏感性分析时完整披露，不能隐藏不利结果或覆盖预先冻结的正式结果。

## 选题停止信号

- 新 seed 的收益系统性低于预先阈值；
- Baseline 方差使合理预算内无法达到分辨门；
- solver 实际只能猜固定 literal，公开函数接口没有真实调用链；
- 正式结果依赖事后挑选 seed、锚点或阈值；
- 关键外部模型、数据或 backend 无法在交付环境获得；
- 每次失败都通过追加 GPU/API 消费绕开，而硬阻塞未减少。
