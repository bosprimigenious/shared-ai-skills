# Agent 独立性、隔离、轨迹与长期运行

## 1. 三个角色分开

专家负责定义任务、参考解和隐藏验收；solver 只看允许的题目与开发反馈；可信评分器从候选重算结果。不要让 solver 读专家研究目录、另一模型输出或 API controller 凭据。普通单人可信研究不需要完整 benchmark 隔离，但凡声称模型“独立解题”，就要把可见范围落实。

两模型从同一个干净任务哈希、同一公共 prompt、同一朴素起点开始；独立上下文和可写目录。原始运行和专家参考研究分开。并行运行本身不会导致独立轨迹自动失效；是否并行取决于资源与规则。单 GPU 通常串行更容易公平地控制竞争。

当两条轨迹部署在租赁 GPU 主机的容器中，使用 `autoresearch-dual-track`：共享同一冻结任务镜像 digest，但分别挂载独立可写卷；peer、Reference、隐藏测试、Docker socket 和控制器密钥均不可见。单 GPU 上容器可同时保留状态，训练/评分仍由可信调度器串行获取 GPU。

## 2. 模型能力要实测

记录实际 harness 版本、provider、请求与返回模型标识、CLI effort 与 provider effort 的映射、上下文限制、工具调用、费用和重试。看到未知模型 fallback warning 需要核查，不等于一定不能用，也不等于可以忽略。

短诊断应走与正式运行相同的接口：模型发起工具 → 固定执行器 → 隔离中的真实操作 → 返回结果 → 模型继续。只发一次 chat API 不证明 Codex 工具链通。诊断时间不自动算正式任务时长。

provider 列出的最高支持档位与命令行可填的最大字符串不是一回事。新任务重新核实指定模型与推理档位，不继承历史项目组合。

## 3. 先使用成熟边界，再考虑自建

优先平台提供的可靠隔离、容器或 VM。没有容器权限而必须自建时，再按威胁模型组合独立 UID、文件权限、Landlock、seccomp、环境白名单、网络限制、进程清理和可信评分入口；这是工程项目，不能靠几行 chmod 宣布等价。

用实际 solver 身份检查：参考解、隐藏数据、peer、凭据、其他进程 proc、目录软链／magic link、冻结文件 truncate/unlink、联网与间接提权。还要正向验证允许编辑、GPU 训练、重载评分和输出写入。记录方法限制与未覆盖项，例如内存／总磁盘配额没有硬限制，就明说。

root controller 可以读取参考解并不自动构成泄漏；关键是模型可调用的操作是否能取得这项权限。如果把任意 shell 原样交给 root，隔离就失效。工具参数只能包含允许的任务输入，不能让模型选择 UID、挂载、角色、评分路径或权限。

## 4. 平台差异的适用范围

宿主设备编号与容器内逻辑设备编号可能不同；不要硬编码宿主 GPU 节点。CUDA 运行时可能需要有限的 proc、共享内存或本地 socket 行为，放行前用跟踪和负测确认最小必要范围，不能为冒烟通过关闭全部边界。某个平台上的静态契约测试不能替代目标 Linux、容器、GPU 和隔离机制的实际验收。

## 5. 原始轨迹与八字段摘要

先保存真实原始事件，再生成摘要。原始记录包括模型请求/响应或 harness 原生事件、工具 argv/input/output、错误、时间、模型标识和实际退出码；适当脱敏，不能捏造缺失推理。

若平台要求，逐轮摘要可使用：`round, policy_name, method_summary, status, score, failure_reason, retained_best, time`。字段名、必填和时间格式以当前平台规范为准。缺少真实方法摘要时保留原始轮并标待整理，不写假合格记录。

每轮绑定不可变 RPC 片段、代码快照、评分和哈希；不要用仍在增长的总日志哈希绑定旧轮。作废或失败新增说明，不覆盖旧轮原文。`retained_best=true` 必须有实际可恢复的方法/产物快照，不只是一个更高分数字。

## 6. 事件边界必须按身份匹配

流里可能包含主线程、内部子代理和其他事件。只有主 thread/turn 的完成才能结束主轮；工具回调、usage 和最终摘要都要正确归属。子代理完成不等于主任务完成，内部子代理没有工具不等于主线程有宿主逃逸。

已有项目曾因错误归属子事件而提前终止主轮，且没有真实评分。修复要有反例测试：注入外 thread 完成、异常 token 和假摘要，确认主轮不受影响。保存旧失败轨迹，不能就地修日志伪装它成功。

API/controller 自身拥有网络和认证，训练环境不拥有。若使用动态工具桥，验证原生 shell、文件编辑、浏览器、MCP、其他可绕行工具的实际可用性；feature flag 名字不能替代负测。升级 harness 后重测关键边界。

## 7. 有效时长与计费时间

若当前规范要求有效时长，把 reasoning、method edit、training、evaluation 与 queue、installation、blocked、idle、sleep 区分。具体分类以来源为准，而不是 skill 自创门槛。

- 推理用真实、完整、同 item/thread/turn 的开始结束事件，缺失、反序和无关事件不补造。
- 工具阶段由可信外部观察器记录实际运行、CPU/GPU 活动，并与冻结 trainer 的 step 日志交叉核对。
- CPU/GPU 活动证明在计算，不能单独证明计算有用；busy-loop 需要识别。
- 不能把整个 turn 或所有 API 墙钟自动记为 reasoning；也不能把“agent 有效时长”错误收紧为“只有 GPU 忙碌时长”。
- 同一轨迹的重叠活动取并集；不同独立轨迹分别核算。内部子代理活动可否计入，核实来源并绑定父任务，不把并行三分钟加成九分钟。
- UTC 与单调时钟都保留；系统睡眠、时钟调整、网络断开带来的缺口明确标记。

达到规定墙钟不代表满足同等长度的有效活动；反过来也不能因为没有 GPU 活动就否认有原生事件证明的真实算法推理。目标时长属于当前题目要求，新题不能照搬旧配置。

## 8. 多轮控制器和监控

持久会话保持同一任务上下文，每轮完整地“假设→改动→验证→解释→下一步”。设置最大 turn、单次工具超时、整体墙钟上限、费用止损和异常停止条件；不能循环重复同一失败命令或 sleep 凑时长。

监控先读状态/进程/原始日志，再决定行动：

- 健康推进：保持安静。
- 新评测：验证全部 seed、重载及快照，再汇报重要结果。
- 失败：保留证据，区分方法失败、训练基础设施失败、认证失败和轨迹记录失败，做有上限的对应修复。
- 长跑结束：核对有效时间和退出原因，冻结最佳方法、备份、按授权处理计费。
- 没启动／仅排队：明确报告，不能说“他们都在跑”。

不要把每分钟大量 observer JSON 发回模型。模型只需紧凑公共指标与证据定位；可信日志保留全量采样。这样既保住证据，又节约上下文和 API 成本。
