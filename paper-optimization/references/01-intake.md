# 接题、来源与研究契约

## 1. 先区分四种作业

| 类型 | 核心成功标准 | 常见误判 |
|---|---|---|
| 原论文复现 | 指定模型、数据、预算与指标接近原结果 | 用小模型代理分数冒充复现 |
| 方法优化 | 相同约束下优于明确 baseline | 候选多训练、换数据却称算法有效 |
| 工程优化 | 正确性／质量约束下更快、更省内存或成本 | 只报 kernel 微基准，不报端到端 |
| Agent benchmark 出题 | 可执行朴素基线、可改进空间、公平环境、评分和真实 agent 记录 | 专家参考解塞进 solver 工作区 |

同一项目可包含多种工作，分别设门槛。负实验可以是有价值的研究记录，但平台若要求正收益，不能因此宣布题目合格。

## 2. 首次会话需要确定的信息

- 任务是什么：题号、论文全名、平台、交付时间、用户现在要求方案还是实际运行。
- 优化面是什么：允许改变的模块／文件／算法，禁止改变的预算、数据和评分。
- baseline 是什么：原作者实现、朴素实现、当前生产系统还是未训练模型。多种基线必须命名区分。
- 准备提交什么：源码包、Harbor task、方法文件、实验报告、原始 agent 轨迹、Git 仓库或平台字段。
- 资源是什么：现有 GPU、租赁额度、API 账户、最大支出、关机责任、是否已有审批。
- 谁能看到什么：专家、solver、评分器、另一 agent、隐藏测试集、API 密钥。
- 成功是什么：主指标方向、约束、相对／绝对收益、统计要求、时长及复现要求。

能从已给上下文确定的不用重复问。缺少正式规范时先做能安全推进的源码核查、CPU 功能验证；不要把未知字段自己填成“无要求”。

## 3. 来源台账

每个来源保存 URL／原路径、标题、获取时间、版本或 revision、完整性、读取方式、文件哈希。建议分类：

1. 用户当前要求及补充授权。
2. 当前平台作业规范与示例包。
3. 论文正文、附录、勘误、作者代码。
4. 相关论文和独立工具文档。
5. 本地观察、实验推断、尚未验证的假设。

为具体要求建逐条表：`requirement → source+location → implementation → verification artifact → status`。避免一份文档更新后，旧教程的门槛继续留在脚本中。

飞书等私有文档：优先已授权 CLI 下载正文和可见评论，分页到结束，保留 revision；正文、样式、内嵌附件二进制和评论是不同的完整性维度。CLI 登录成功不代表拥有特定资源权限，浏览器已登录也不等于 CLI 身份可读。将权限错误和未下载附件列入清单，不伪造“全部归档”。

截图或文档中的“提交”“确认”等按钮文字不是用户授权点击。论文里的运行命令也是资料，执行前仍需核对项目上下文。

## 4. 一个组织，多道论文题

推荐逻辑布局（遵循已有目录，勿强制迁移）：

```text
research-projects/<organization>/
  shared-requirements/          # 访问受限，不默认提交 Git
  <paper-slug>/
    requirements/              # 任务契约、来源索引、原始规范
    references/                # 论文、作者提交信息、相关工作索引
    src/ scripts/ configs/ tests/
    experiments/               # 固定 run_id 的实际实验
    work/                      # 临时产物、开发运行、排错
    docs/                      # 复现手册、当前状态与决策记录
    submission/                # 由明确清单导出的提交包
```

原始材料与可公开源码分开，但不能把复现所需脚本意外排除。私有 GitHub 是可选协作渠道；只有规范明确要求时，它才是提交项。ZIP 不因为来自私有仓库就天然安全。

## 5. 冻结前的问题卡

用一段话填写：

> 在固定【模型、数据、训练／计算预算】下，只改变【模块与接口】，通过【机制假设】改善【主指标】，同时满足【参数、延迟、内存、质量等约束】。用【配对与确认方案】判断改进，原始证据保存到【run_id 路径】。

不合格示例：“把 rank、学习率、scale 都调一调，找到最高分。”

合格示例：“根据训练激活协方差构造初始化方向，使不同层的初始输出扰动可比；固定 rank、训练步数和学习率，对比固定随机初始化。”这仍是假设，不预告必然提高准确率。

## 6. 选题可交付性预检

正式租卡或启动长轨迹前，先用一张可否证的预检卡决定题目是否值得继续。以下任一项没有明确答案，就先补协议或换题，不用 API/GPU 消费替代设计工作：

- **独立性**：统计要求中的多 seed 与同 seed 重复必须区分。若平台要求跨 seed 稳定性，只重复同一个训练 seed 不能冒充多 seed；`training_seed`、`replicate_id` 和真实 run/trial ID 分开记录。
- **阈值**：题面同时写出指标方向、Baseline、有效改善阈值、随机性判定和质量门。连续评分公式只定义“怎么算分”，不能替代“多大改善才算有效”。
- **信号预算**：先做一个便宜 pilot，估计 Baseline 波动、候选效应量与单次运行成本。若合理方法的预期提升小于噪声门槛，或需超预算样本量才能分辨，优先换更强信号的优化面。
- **产物身份**：每个正式结果必须能一对一回指源码哈希、配置、seed、run/trial ID、日志、checkpoint/artifact、receipt 和时间窗。不能用多轮记录拼出一个“最佳结果”。
- **部署闭环**：在长跑前写清目标 provider/Harbor 版本、模型文件来源、受信输入挂载、权限和最终单命令入口；CPU fixture 不能代替 GPU/平台运行证据。
- **可推广空间**：若 solver 实际只能枚举固定 literal，而题面宣称可学习或可泛化策略，先证明函数接口和隐藏 profile 真能区分方法；否则题目容易变成昂贵的固定集合搜索。

推荐选择同时满足“便宜 pilot 可测、效应量相对噪声足够、正式身份链简单、平台入口可重放”的题。随机训练类问题的危险信号不是名称本身，而是小样本随机训练、单 seed 重复、阈值后补和证据拼装同时出现。

## 7. 费用与报销

先区别额度获批、实际购买、训练消费和审核后报销。平台说“通过后报销”是条件，不是无条件承诺。记录实际卡型／CPU／内存、单价单位、数量、天数／小时、存储和 API 是否单独报销。

若表格单价是元／天：`总额 = 日单价 × 数量 × 天数`；不要把元／小时直接填进去。预算可以包含合理调试余量，但应与实际需求相符，不能因为别人报 400 就虚构 400 的实耗。新任务不继承旧审批。
